# City Performance

Version 0.5.0, the first Workshop candidate. City Performance is an experimental performance and diagnostics mod for Big Ambitions. It runs in a game with no other mods: on the audited Windows game build it installs its vanilla hooks, with all behavior features and experiments enabled by default and logging disabled. Features for other mods start only when those mods are loaded. Bakery Help needs Bakery, faster lamp discovery needs POLYMODS HYPERREAL, and camera-aware coverage needs the HART Free Camera bridge. On any other game build, including the Mac game and the next game update, the game's own hooks stay off and only timing and trace hooks run; faster lamp discovery can still run on the Mac, because its audited Unity pair includes the Mac one. **Offline checks do not establish native behavior or a performance gain. The 23 October native Mac integration checked all 13 fresh option defaults and coexistence through midnight and save/reload. Windows behavior, visuals and performance remain unverified. See [release readiness](docs/release-readiness-0.5.0.md).**

## Conditional Hyperreal discovery

Those measurements cover the complete method; they do not establish how much time Unity spends sorting. This candidate replaces exactly its `FindObjectsOfType<HDAdditionalLightData>(true)` call with `FindObjectsByType<HDAdditionalLightData>(Include, None)`. Unity documents unsorted discovery as requiring fewer resources ([Unity 2022.3 API](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/FindObjectsSortMode.None.html)). The global search and result allocations remain. No FPS or hitch reduction is claimed yet.

The eight-second cadence, inclusion of inactive objects, new-lamp baseline capture, foliage refresh, light adjustment and restoration all remain Hyperreal's original code. Discovery is still performed when Hyperreal's enhancements are off. There is no retained light cache, scene traversal, delayed discovery or additional per-frame search. Result order changes; native identity-set and final light-state parity require a playtest.

Activation waits until city-ready and detects optional Hyperreal load order without forcing the mod to load. The `hyperrealdiscovery` setting defaults on; turning it off removes only this feature's transpiler. City/mod unload also removes it. An absent Hyperreal is inert. Unknown binaries, unexpected IL and conflicting patches leave Hyperreal's original/composed behavior intact and log a specific `Hyperreal discovery: inactive` reason. A detected incompatibility latches the feature inactive until City Performance reloads; toggling the option does not override that safety decision. Query exceptions propagate without retries or suppression.

The audited Hyperreal DLL SHA256 is `7d1bd589947558e2f3cc476f06d4699618732835718ffd2335f2e5102cfcef10`. The exact Core/HDRP pairs are recorded in `HyperrealDiscovery.ReviewedPair`; cross-platform mixtures are refused. This validates the adapter's managed contract, not the native engine implementation. It is independent of `PerformanceMod.Verified`, which continues to gate the other behavioral changes.

**Hard Mode Patch coexistence:** its older lamp-cache hook takes precedence whenever installed, even if its setting is off. City Performance refuses that existing hook. A later default-priority same-call transpiler is preserved and this feature withdraws. HMP 0.4.2 removes that hook and retains its independent map-return workaround; the new pair coexists. Installing CP alone does not remove an older HMP hook. The previous full-pack Windows cache remains a separate implementation; do not claim this candidate is active without checking its activation log. Foreign patches on the audited StreetLights consumers or Unity query/conversion boundaries also disable substitution before the next optimized query. Detection uses Harmony’s shared registry; raw/native detours, incompatible Harmony copies and unrelated downstream HDRP hooks are outside that guarantee. The offline shared-generic checks verify detection logic on CoreCLR, not Mono execution. Unsorted order can also change partial application order if a downstream light operation throws.

## Background autosave prototype

**Background autosaves (experimental; validates first save)** defaults on in Settings → Mods → City Performance. The first eligible recovery or midnight autosave in each loaded city still uses native saving. The mod also captures a detached snapshot and compares its serialized bytes against the native writer's uncompressed staging file. Only an exact match enables background serialization for subsequent eligible autosaves. New runtime types, value types or collection comparers trigger native validation again. With the option left off, no save hooks or native save-method bindings are installed; enabling it installs the guarded feature. Manual saves, old-age backups and JSON saves retain the native path. Native save callbacks, rotation, names, thumbnails, metadata construction and economy timing stay at their original call sites.

Capture is synchronous on the main thread, after save callbacks have collected the current state. Compiled copy plans preserve persisted fields, aliases, cycles and collection ordering, detach mutable values and clear omitted runtime caches. Boxed mutable values are copied while preserving aliases. Custom serialization records, collection subclasses and unapproved ordinary-record formatters are refused. Both strong and weak Odin formatter caches for the exact worker policy warm on the main thread; unexpected warnings or errors refuse the capture. The worker receives that frozen graph and staged metadata; it never traverses the live city. It uses the shipped Odin binary format and save policy with its own serialization context and logger, then native-compatible gzip compression. This prototype does **not** yet accumulate changes across frames. Doing that consistently requires tracking every relevant mutation or retaining older versions of changed records.

The first capture has a soft 1,500 ms abort budget for cold code generation; later captures have 500 ms. These are refusal thresholds, not frame-time targets. Work is checked periodically, and one allocation/operation can exceed the threshold. A refused capture falls back to native saving and disables the experiment until restart, so that save can take longer than vanilla. Formatter warmup adds main-thread work outside the copy budget, and validation itself adds capture and worker comparison work. The release defaults this experiment on; disable it if that extra validation cost or save behavior causes problems.

The worker waits until native metadata preparation has completed, runs below normal priority and uses unique staging files. Validation retains the native requested compression priority; only the subsequent comparison work is lowered. A lifecycle drain never lowers a higher native priority. Before replacing either file, publication copies a complete preceding data/metadata pair. It then replaces save data and metadata separately on the same filesystem, retaining those recovery copies as `.cityperformance-previous` and `.cityperformance-previous-metadata`. These names do not create extra native save slots. Publication errors independently attempt rollback of both attempted targets, including replacements that changed or removed their target before throwing; failure is logged and surfaced to the player, the current source is marked dirty and future saves use native behavior. **The two-file publication is not a crash-atomic transaction:** forced termination between replacements can leave stale metadata, and there is no automatic crash-recovery journal. The retained data and metadata allow manual recovery. Backups are retained indefinitely and can become orphaned when native slot rotation deletes a save; there is no automatic backup cleanup. If only one current slot file exists, its absent backup counterpart is removed to prevent a misleading pair; an older recovery pair is preserved when neither current file exists. Screenshot generation still follows the native lifecycle.

Only one job runs at a time. Save progress remains active until completion is processed on the main thread. A subsequent save, native join, city/mod unload or normal quit drains the worker; those boundaries can wait and promote the worker to normal priority. Audited native serialization, feedback-save and loading entry points share a gate with worker serialization and warmup. Asynchronous loads reserve it until their returned task completes, including cancellation or failure; captures use native saving while that reservation is active. Disabling the option lets an already captured job finish. Native exceptions keep their identity and propagation. Exact hashes of the nine audited game/serializer dependencies are required. Foreign hooks on the save path or Odin, custom formatter registrations, unsupported snapshot types and known multiplayer assemblies refuse the experiment. Compatibility inspection failures disable the experiment without escaping into native saving, and missing or duplicated transpiler targets leave the incoming instruction stream intact. A later detected conflict stops new background jobs; it cannot undo a job already running.

`AUTOSAVE` entries record mode, frame/day, preparation, capture, main-call duration, worker serialization/compression/publication, allocated bytes, capture GC counts for generations 0/1/2, graph sizes, validation/error status and the six most expensive capture sections. The last 32 reports and current guard state are included in exported capability metadata. An unavailable or nonpositive allocation-counter delta is reported as -1, not zero allocations. If the optional allocation API throws or is unavailable, the protected capture falls back to native saving and disables the experiment. Worker durations are elapsed times, not main-thread frame costs. The native serialization timer excludes the new worker; compare the whole autosave frame and `main_call_ms`, not that timer alone.

Two copied saves passed an offline native-writer comparison, native-loader reload and mutation-isolation check: about 429,000/647,000 captured objects and 58.7/85.8 MB of serialized data. Capture allocated approximately 61/74 MB. Warm capture timings varied roughly 120–600 ms across harness runs; these are **not Unity measurements or established hitch reductions**. The harness runs the actual Windows Odin library on .NET 10, disables its legacy dynamic formatter emission in favor of its built-in reflection formatters, and substitutes Unity logging while checking for unexpected warnings/errors during reads, warmup and serialization. The host-only .NET 10 default string comparer has one explicitly identified legacy-Odin warning; the harness isolates that formatter warmup before the tested phases. No such exception is permitted in production warmup. Initial fixture loading and output reload use the actual native loader, including its legacy migration. It checks format/copy behavior but cannot establish Mono thread safety, GC behavior or in-game frame cadence. Building registrations dominate the copied graph and are the next likely target if capture remains too expensive.

For a controlled playtest, use a copied save and enable trace capture/extra diagnostics before autosaves. Keep other options identical between baseline and experiment. Confirm the first `mode=validation` reports `byte_match=True`, then observe several `mode=background` saves, including a midnight and a recovery save. Export the trace after completion. Reload resulting saves and check balances, inventory, employees, businesses, vehicles, time and mod data; exercise manual save, option disable during a pending job, city exit and normal quit. Compare whole-frame stalls, capture allocation/GC and worker duration. A shorter serializer span alone does not establish smoother recording.

## Camera coverage and audio

Pair this package with **HART Free Camera 1.1.1**, whose optional protocol-1 bridge exposes only its active world recording camera. It never exposes the preview presenter, blank display camera or UI. Since 0.5.0, coverage starts only when that bridge is loaded. Without it, the game keeps its own coverage, far clip, decal distance, traffic observers and audio, and the log says so once. Earlier versions also widened main-camera coverage without the bridge. Coverage and camera audio start enabled unless the player has already saved a different choice. Preserve the existing `second-screen-spike.json` when updating HART; its standard build package deliberately does not supply that private configuration.

Camera-aware coverage merges the native player bands with both cameras' expanded viewing volumes. The second camera also gets an all-direction nearby bubble, so turning a shot does not expose an immediately empty foreground. Distance is measured on the ground for aerial views; the viewing volume is still three-dimensional. For the audited 60/200m bands, 150% extends the forward bands to 90/300m, and 200% to 120/400m. Both views retain a 20% projection margin and recently needed detail has a two-second release grace period. The feature raises an insufficient camera far clip while active, preserves larger values and restores the value it owns on disable.

Native proximity callbacks activate street lamps/signs, foliage effects, benches, hangouts and stationary character zones, plus the game's other registered proximity content. Added transitions share two callbacks per rendered frame and a 128-entry/soft 0.75ms world-scan budget. A single native callback, traffic setup or pedestrian acquisition remains indivisible; these are not hard frame-time limits. Existing stationary-zone smoothing can further spread those zones' coroutine work. Remote coverage can take time to fill after a cut or teleport, and outside-interactable batches retain their known native behavior.

Walking street life gets up to **20 extra pedestrians**, separate from the player's requested pedestrian list. They use native pools, real door/navmesh positions and local destinations. Acquisition is limited to one per quarter-second, with one-second backoff when no hidden valid door is found. Spawn points visible to either expanded view are refused; wide aerial shots can therefore remain sparsely populated. Native pedestrians can stay active in camera coverage. Traffic uses nearby/midpoint/forward observers for each view, keeping the native vehicle pool size, density and 80m removal radius. The native vehicle cap is shared across views, so density may become thinner. Traffic coverage is an overlapping corridor of native grid areas, not exact coverage of every point in a wide camera frustum. Observer swaps rebind the manager, grid and visibility arrays together; failed swaps restore references before disposing buffers. Invalid map-edge observer positions fall back to the player.

Recording-camera audio repositions the **existing single listener**, including rotation, and uses the recording position for native distance-gated sound sources. Sound-only AudioZone triggers are evaluated at that camera at 10Hz using their real colliders and native fades. Turning the camera or audio option off returns the listener and owned sound zones to the player. No player transform or gameplay collider is fabricated. Global/UI/non-spatial audio keeps its ordinary mixing behavior. The HDRP decal distance ceiling also scales with the coverage setting, capped at 400m while retaining authored per-projector limits. Fog, sun-shadow distances, custom unregistered proximity systems and asset-specific disappearance may still produce their own cutoffs.

The base game hash below is required. Traffic additionally requires `ExternalPlugins.dll` SHA256 `7d43e9d42d2f464674cff045bcb048c48e0f87aec0a987baa34122ac6e3415d1`; decals require Windows HDRP SHA256 `d0f869303996388151aa45aefb90c33147f0ae7961a1d0e0b406015ad5a8dfc6`. Foreign hooks on the affected methods disable the corresponding feature. Failed installations remove only that feature's partial hooks. Later conflicts yield control and restore owned state. No RLO files are modified; the Harmony changes remain in this mod.

`CINEMA` summaries report coverage/audio/bridge state, scans, transitions, deferred work, maximum coordinator time, extra pedestrian acquisitions/rejections and traffic status. Trace metadata records the current cinematic settings and guard state. These are not visible-object counts or measured FPS gains. Compare the same warmed route at 100%, 150% and 200%; test a remote hold shot, a driving follow shot, an aerial view, fast turns and camera on/off. Check player-area population, gaps/pop-in, visible spawns, audio position and ambience fades. Also test option disable, map and building entry, a city reload and a return to the title screen. Export a trace from each run. The extra distance is a visual-quality tradeoff and may cost CPU/GPU time even with the existing performance options enabled.

## Tree detail experiment

The audited Windows `TreeController.Start` forces mesh LOD0, and its map handler forces LOD1 while the normal map is open and LOD0 on return. The distance-band `OnLod0/1/2` callbacks only control falling-leaf particles. Separate view-blocking fades, screenshot layer changes, shadows and global detail bias can still change a tree's appearance. An observed drone-shot change alone does not establish which mechanism produced it.

The asset audit found 500 Manhattan trees with two real meshes, both included in the existing view-blocking fade list. Their second meshes have 31–65% fewer triangles (49% weighted across that serialized set). A contextual inspection of the local Mac Hamptons scene found 4,195 more tree controllers and different mesh families; **that is not a live Windows tree count or an FPS estimate**. The runtime accepts these families only if the actual Windows mesh names, vertex counts and triangle-index counts match the inspected pairs. Unknown layouts, other map-switcher components and missing fade coverage are skipped and counted.

The option returns eligible groups to Unity's automatic camera-based LOD selection (`ForceLOD(-1)`). It does not select a level based on the player or main camera, so a recording camera can independently retain a close-up mesh. The first transition is capped at 15% screen-relative height (before the existing LOD bias), retaining detail longer than most authored thresholds; an already smaller threshold stays smaller. The last threshold becomes zero to keep the real distant mesh instead of introducing the assets' distance disappearance. Native camera clipping, visibility and shadows still apply. Existing crossfade modes/widths, renderer enabled state, materials, property blocks, particles, layers, RLO detail bias and maximum-LOD settings are preserved. Trees authored without crossfade can still switch visibly; this is deliberately not a new shader or tree impostor implementation.

[Unity ForceLOD reference](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/LODGroup.ForceLOD.html) and [LOD Group reference](https://docs.unity3d.com/2022.3/Documentation/Manual/class-LODGroup.html) describe automatic selection and screen-height thresholds.

Setup consumes at most 32 registry entries/reapplications and a soft 0.75ms budget per frame; an indivisible Unity operation can exceed that. It reads `TreeController.AllTrees` incrementally, without a world search or a repeated per-camera tree traversal. Map mode temporarily restores the game's forced selection, including the low-detail-map early-return case, and automatic selection resumes after the close animation. Changing the option or unloading restores owned LOD definitions and the tracked vanilla forced level. A changed definition is left to its new owner. A foreign Harmony patch on either tree initialization or map switching refuses the experiment; a later conflict restores owned definitions and leaves forced selection to the foreign owner. The game's global `ForceLOD0` override also disables the experiment.

`TREE` logs and exported metadata show installation/request/fault state, registry progress, skip reasons, map hold, detail bias and configured records. Configured records are **not visible-tree counts, actual selected LODs or measured GPU savings**. Frame CSVs append tree request/fault/configuration/map/setup columns so option changes and setup frames can be excluded from comparisons. Setup is temporary, but native LOD selection/crossfading has ongoing engine cost.

For acceptance, compare the same warmed-up route with the option off/on in Manhattan and the Hamptons, including a high drone shot, low passes through trees, zoom/FOV changes and a second recording camera far from the player. Check silhouettes, shadows, fades, distant visibility, map open/close in both map-detail modes, option disable, city reload and mod unload. Keep RLO detail settings and recording resolution identical. Export each run after setup settles; compare frame cadence and camera/GPU counters where available. No FPS or hitch reduction is claimed until that test.

## Midnight cleanup experiment

Only the `Resources.UnloadUnusedAssets()` call inside the exact audited `GameManager.NewDay` is intercepted. The transpiler requires exactly one call followed by a discarded return; unknown builds, changed call shapes and foreign patches refuse the optimization. Daily economy, wages, notifications, portraits, game events and saves still run at their original time. Cleanup calls from other code are untouched. With the option off the original Unity operation runs at the original call site.

A pending batch runs under an active, fully opaque black overlay or a loading screen when possible, provided the optional HART bridge does not report an active recording camera. The bridge is refreshed for this check even if camera coverage/audio is disabled. Otherwise the oldest request has a five-minute real-time deadline by default (plus up to 250 ms polling when frames are running). The slider permits one to ten minutes; increasing it cannot extend an existing batch, and reducing it shortens the pending deadline. Several accelerated game days can therefore share one sweep. Requests are queued until a scheduler poll, including requests made during a hidden screen or memory pressure, so active saves or our previous cleanup can finish first.

A Unity low-memory notification, 256 MiB growth since the oldest request, or tracked allocations reaching 80% of reported system RAM triggers earlier execution. Missing/invalid allocated-memory telemetry disables batching and falls back to a cleanup. These counters do not measure all process/system memory, so the hard deadline remains necessary. Multiple waiting requests preserve the oldest time and memory baseline. Disabling the option drains the request on the next unblocked poll. City/mod unload flushes it; application quit retires it because the process is exiting. Known Going Public assembly names, including `BigAmbitionsMP`, disable deferral even when loaded later.

**This can reduce the number of sweeps; it does not make an individual sweep cheaper.** Unity's sweep is indivisible and may still hitch at the deadline or memory fallback, including during cinematic recording. Fewer sweeps temporarily retain unused assets longer. The five-minute default is a bounded experiment, not a demonstrated optimum; use one minute for the previous timing baseline.

`CLEANUP` log entries record the queued and execution frames, batch size, deadline, reason, wait, call-return duration, completion latency and Unity allocated memory before/after. Completion latency includes asynchronous execution and polling delay; it is not CPU time. The call-return duration may exclude later native work. The signed observed memory drop includes intervening game allocations and is not an exact count of reclaimed asset bytes. Unavailable readings are explicitly marked. Export metadata includes these fields plus request/execution/coalescing counts and pending/fault state. Exceptions from an original Unity cleanup call propagate; a consumed failed request is not retried.

The October 20 rendered PC AI tests motivate this change: two long exports recorded 32 requests, 32 separate executions and zero coalescing with the old one-minute bound. The latest run's native timing lines measured 15 sweeps at 415–526 ms, sometimes freeing only five or six assets. Other recurring spikes follow Hyperreal’s eight-second discovery cadence. The older Hard Mode Patch discovery hook was refused on the modified test-rig game assembly. The conditional adapter above is a new candidate; its effect has not been measured. Neither this package nor its compatibility checks changes that rig or Hard Mode Patch.

## Stationary-zone experiment

The audited `StationaryAiSpawner.SpawnGroupOverFrames` iterator activates at most one performer, homeless character or ordinary stationary character in each `MoveNext`. Its first step runs immediately inside culling; subsequent steps resume as independent Unity coroutines. The new hook wraps that **actual iterator** and delegates the original step only when one shared budget allows it. It does not merely wrap an outer culling callback.

The scheduler permits at most four steps and 2ms of observed step time per rendered frame across all participating zones. It checks before starting the next step and accounts completed or failed work in `finally`. One indivisible activation can exceed 2ms; this is not a hard frame-time guarantee. One step per zone per frame preserves the original coroutine's frame spacing. FIFO rotation avoids a fixed early-zone preference. An exhausted budget adds `yield null` waits; it does not discard the remaining original iterator.

The original iterator retains all position reservation, probability/random selection, pool acquisition, performer orientation and private character bookkeeping. The mod never releases those characters itself: vanilla `ClearPedestrians` owns release. A bounded queue holds at most 128 zones; overflow runs that new iterator normally and records a trace overflow marker. A replacement invalidates the previous zone ticket. Clear, invisibility, disabled/destroyed zones, city replacement, map opening and loading invalidate pending work. Pruning prevents a stopped/destroyed coroutine from blocking the queue head. Existing actors remain subject to vanilla release rules.

Turning the option off lets an already-wrapped original iterator continue at vanilla cadence. Removing the mod in an active city also releases its budgeting on subsequent resumes. ## Traces and interpretation

Enable trace capture before a take. With **Automatically save trace** enabled, leaving the city or quitting normally writes the latest 8,192 frames, the 128 slowest focused frames over 50ms from the whole session, an additional bounded method-call CSV when detailed diagnostics captured calls, and metadata with whole-session focused frame statistics, graphics settings, loaded assembly identities, and available hooks/counters. Earlier hitches remain available after the recent-frame ring rolls over. The hitch file is a selection of outliers, not a representative frame distribution. Optimization selections and version verification are included in each completed frame row. The first frame and focus transitions have unavailable wall duration instead of a misleading gap.

Files go to the game's `Application.persistentDataPath/CityPerformanceTraces`; the normal mod log reports the exact path. Automatic export finishes synchronously at the city/mod unload or normal application-quit boundary so exiting does not kill an unfinished background write. There is no automatic trace disk write or snapshot allocation on a hitch. The fixed-size hitch archive copies completed rows in memory. A crash, forced termination or power loss can still lose the current in-memory session; use **Export current trace** to preserve an interim snapshot.

Manual exports use a background task that only sees copied records and strings, never Unity/game objects. At most one manual export runs at once. A final automatic export may overlap that manual write, using separate snapshot data and a unique filename. Snapshot allocation happens on explicit export or teardown, so manual export during a take can itself disturb that take. City teardown clears the ring and hitch archive. No proprietary game content is exported.

Rows use Unity rendered-frame IDs. A `WaitForEndOfFrame` coroutine takes monotonic end-to-end wall samples after rendering; the first sample after enabling/resuming is unavailable. This measures delivered frame cadence including waits/OS effects, not just CPU execution. A focus flag helps identify background periods. A host `FixedUpdate` counts actual fixed steps. Main-thread method costs are associated with their rendered frame:

- stationary iterator execution, general refill and outside-interactable spawning;
- culling controller update, traffic FixedUpdate, main game tick, save serialization and nearest-building `TryGet`;
- hourly/save-event markers, exceptions, cumulative GC collection counts;
- pending stationary work and oldest request age;
- sampled active/capacity traffic counts (sample frame explicitly included, at most once per 30 frames; scans above 4,096 slots are refused);
- current/desired texture memory and pending/loading texture counts.

Scopes are **inclusive** and overlap (for example culling may include spawning), so do not sum all columns. Background serialization is excluded from frame attribution; the cheap aggregate timer can still include it. GC columns are cumulative: differences between rows show collections. Loading/teardown can leave a partial row with no wall timestamp. The trace includes both focused and background operation; use matched focused routes for controlled comparisons.

Profiler counters are discovered at runtime with descriptors/units. Only exact names and units are accepted. The base counters are GPU/Main Thread time and per-frame allocations. Extra diagnostics also request GC collection time, used/reserved GC heap, render-thread time, PlayerLoop, script Update/LateUpdate, physics, UI and present-wait counters. Release builds may omit some or all broad-phase markers; the capability file records which actually started. The exported capability file lists discovered names and units. Their columns contain the **last available recorder sample**, which can be delayed; they must not be treated as precisely aligned to that row's frame. Missing/empty counters and missing method hooks are `NA`, never zero cost. Traffic counts use -1 when unavailable. Actual VRAM headroom is not established by these texture-memory counters and is not invented. The game ships without enabled FrameTimingManager statistics; this mod does not assume GPU data exists.

Capture startup discovers counters and allocates recorder state. Detailed hooks install after the city is ready, outside the hourly callback. These frames have `diagnostic_setup=1`; they remain in the raw trace/hitch archive, so exclude them and warm-up from comparisons. The recurring hot path uses fixed arrays, structs and counters; Harmony guards and Unity/profiler calls still have overhead that must be measured.

## Extra diagnostic exports

Each export includes the normal frame CSV, `-hitches.csv`, `-methods.csv` and `-capabilities.txt`. Method storage has two separate rings: 4,096 recent calls taking at least 1 ms, throwing, running a known game `RunHourly` helper, or handling a selected string game event; and 2,048 protected calls made inside `GameManager.NewDay`, including fast children and the root itself. The CSV appends `day_boundary` to identify that context. Frequent shared callbacks cannot evict daily records. Both rings are bounded, with separate overwrite counts; all timed calls still contribute to session counters. Metadata maps method IDs to names. Method timings are inclusive wall time and can overlap each other and the main game-tick span; never add them as independent costs.

The exact verified game tick supplies the hourly helper targets, and the audited NewDay supplies daily helper targets. Loaded Food Trucks catering methods (`OnNewDay`, `Offer`, `Places`, `Caterers`, `CategoryUnits`) receive timing-only hooks. `kind=Hourly` describes hook provenance: a shared helper such as `UpdateDynamicComponents` is timed on every invocation, including non-hourly UI updates. Current `onNewHour`, `onNewDay` and string game-event subscribers are discovered at setup without changing their order or delegate lists. String game-event callbacks record only new-hour/new-day events. Later subscriber registrations require toggling extra diagnostics off/on. Calls to the same callback method on multiple instances are aggregated. Loaded Camera Tools discovery methods are timed without forcing the mod to load.

Camera IDs/names map to fixed 16-camera storage; overflow is reported. Camera time is the CPU interval between render-pipeline begin/end callbacks, **not GPU cost** or a full measure of camera setup. Nested callbacks can overlap. Frame rows also record refill fault/pending state, current target, active count and remaining finite acquisitions, allowing eventual completion and stale backlog to be checked. Unavailable refill counts are -1. GC mode is included in metadata; this mod does not change GC settings.

## General refill behavior

The original full target is retained while an initial finite acquisition deficit is spread over frames. Departures cannot extend the acquisition budget indefinitely. New requests replace old targets; reductions stay vanilla. Disabling the option flushes remaining acquisitions (potential one-time spike). New city/spawner ownership, loading or interior entry cancels stale pending work. Exceptions disable this experiment; original-call exceptions are preserved. Deferred failures are logged and not retried, avoiding duplicate partial effects. A newly conflicting patch cancels pending refill without invoking the conflicting chain.
