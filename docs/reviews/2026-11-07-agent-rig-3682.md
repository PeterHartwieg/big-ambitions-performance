# Agent-rig copy of build 3682: save-guard composition audit

7 November 2026. City Performance now accepts a second `BigAmbitions.dll` digest, `095db57964c85ebb293067ae4699002b383c6d7cfe81674ce15c58ed9fc628ed`. This is the agent rig's patched copy of the audited Windows build 3682 (`9427561b81aaab2ada09c22a3c98dd9a4017a65225b389513885bf336852e911`) at `C:\BigAmbitions-AgentTests` on the home PC. It is not a second game version. The live-game digest is unchanged. Any other digest, and a failed read, still leaves `Verified` false.

## What the rig changes

I compared every method body of the rig DLL against vanilla 3682 with a throwaway Mono.Cecil tool. The rig DLL was copied read-only from the PC; nothing on the rig or its lease was touched.

- 24,067 methods in both. 24,065 bodies are identical.
- `SaveGameManager.Save(SaveType,string,string)` has 7 more instructions: `ldarg.0; ldc.i4 0 (Default); ceq; call AgentTests.Host::AllowSave(bool); brtrue <original first>; ldc.i4.0; ret`. Instructions 7 onward match the vanilla body exactly (243 of 243), and the one `finally` block has the same range.
- `HGModLoader.TryInitializeModsForPlaySession` gains a leading `call Host::MarkSaveGuard()` and calls `Host::get_IsReady` instead of `SteamAPI::get_isRunningAndValid`. CP does not hook this method.
- Types, fields, method signatures and attributes are identical. The only new assembly references are `AgentTestRuntime` and `netstandard`.
- The eight other assemblies pinned in `GameSaveSnapshot` have the same digests on the rig as in the audited set.

This matches agent-rig `runtime/Patcher/Program.cs` and `RigSaveGuard.Apply` at cfcc5fd. The deployed `AgentTestRuntime.dll` (`4a248b40…`) implements `AllowSave(manual)` as `!rigTest || manual`. The repo's newer `SaveGate.Allow` keeps that rule when no save-specific mode is set, and adds one-shot `ArmSave`. Either way, under `-rig-test` the guard refuses natural midnight and recovery saves.

## Overlap with BackgroundSaves

The Cecil guard sits in the same method CP's BackgroundSaves patches. Allowlisting the rig digest turns `Verified` on, so BackgroundSaves installs on the rig along with refill and every other behavioral feature. Before this change it stayed off there. `GameSaveSnapshot` and `BakeryHelp` had their own copies of the 3682 digest. Both now use `GameBuild.Audited`, so the rig runs the same feature set as a live 3682 game.

Why the composition is safe:

1. Harmony builds its replacement from the method's current IL, which already contains the guard. The order is prefix `Begin`, then the guard, then the native body, with finalizer `End` around both. `Begin` only marks `MidnightSave`/`RecoverSave` eligible. It writes nothing; at most it drains a previous job.
2. When the guard refuses, Harmony turns its `ret` into a branch to the epilogue, so `End` gets `__result == false`. `Capture` replaces the `SerializeSaveGame` call, which comes after the guard, so no snapshot or job exists. `End` only restores the call stack. No worker starts and no file is written. If a job did exist, `End` marks it aborted when `__result` is false, and `Worker` throws before writing any temp file.
3. `Rewrite` matches its four call sites by operand: `SerializeSaveGame`, the `CompressSaveGame` ldftn, `File.WriteAllText` and `Thread.set_Priority`. The guard calls none of them, so each still appears exactly once. `Rewrite` copies every other instruction untouched, including the guard and the label its `brtrue` targets.
4. `Conflict()` sees only Harmony owners. The Cecil guard is part of the method body, not a patch, so it does not block installation. That is correct here: the guard runs before any code BackgroundSaves depends on, and a refusal leaves CP state unchanged.
5. Manual (`Default`) saves pass the guard and keep the native synchronous path, as on live. Ordinary rig sessions (no `-rig-test`) and armed save-specific flows pass the guard and then behave exactly as on live 3682.

Separately, `CityPerformance.cs` times `SerializeSaveGame` with a Harmony prefix. That method is not a guard target and is byte-identical on the rig.

## Evidence

The new offline check runs CP's real `Install`, `Begin`, `Rewrite` and `End` on the rig DLL:

```
dotnet run --project tools/SaveCheck -c Release -- <scratch Managed with rig BigAmbitions.dll + AgentTestRuntime.dll> --rig-guard build/CityPerformance/CityPerformance.dll
```

It passes 19 checks. The shipped hash read verifies the rig digest, and BackgroundSaves installs. `Rewrite` changes four sites, all after the guard, and leaves the guard intact. Under `-rig-test`, `Save(MidnightSave)` and `Save(RecoverSave)` run `Begin`, which marks the save eligible. The guard then refuses it, and `Save` returns false. No job or pending worker is left, and nothing is written to the save directory. BackgroundSaves stays installed and unfaulted. Only refused saves execute; an allowed save would enter Unity code, which cannot run offline.

`tools/DetailCheck --vanilla` on the same scratch Managed folder:

- main d260b99 (before): `audited=False`, only timing/trace hooks install, BackgroundSaves stays off.
- this branch (after): `audited=True (agent-rig copy of 3682)`, every vanilla feature and background autosaves install. 53 checks pass.

On the audited 3682 refs, `--vanilla` (53), `--button-captions` (17), `--slider-labels` (20), `--cinematic` (28) and `SaveCheck --hooks` (43) still pass. The pure tests cover `GameBuild.Audited`: both digests are accepted, and null, empty, uppercase, truncated, padded, the Mac rig digest and the Mac game digest are refused.

I did not run `OwnershipCheck`, so the Bakery digest call is checked by compilation only. I did not run `--trees-only` either, since it needs a HART camera DLL. None of this is runtime validation in the rig. A `rig_test` session on the PC still has to show BackgroundSaves installed and midnight saves refused without CP writing a file.

PR #1 (c005162) does not touch BackgroundSaves, GameSaveSnapshot or the hash gate. This audit applies to it unchanged.
